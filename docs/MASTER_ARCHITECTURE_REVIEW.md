# Master architecture review

**Current review branch:** `lunyx/full-client-quality-pass-v1` (Draft PR #159)  
**Historical integration base:** `lunyx/safe-mode` at `684333a2edce978cc7673ae3277c4d65d92f1d63`  
**Scope:** architecture and static source review of the integrated Java/Fabric client, its build/rebuild workflows, persistence, networking, profiler and multiplayer-facing modules. This report records observed contracts and verified risks; static inspection is not runtime validation.

## System map

### Startup and ownership

`ClientInitializer` builds the shared services in dependency order: event bus and manager services, module registration, HUD module registration, command registration, event publication, then configuration manager setup and configuration loading. `ClientContext` exposes much of this state through mutable static references. That is a practical fit for this single-client process, but it makes construction order and test isolation important. GUI screens are created lazily from the same shared context.

Modules register their event handlers when enabled and unregister when disabled. The quality pass makes enable transitions rollback-safe and keeps the disabled state authoritative even when cleanup callbacks fail. Module-owned delayed work can now be cancelled through the bounded scheduler on disable, reducing the need for ad-hoc lifecycle flags. HUD widgets are module-backed and use the same settings and persistence model as ordinary modules. There is no separate per-world module container; subscribed listeners live for the client lifetime or for the module's enabled lifetime.

### Events and threading

`EventBus` scans annotated one-argument, void methods during registration and caches listeners by event class. Instance lookups use identity semantics; static listener lookup is concurrent. Per-event arrays are immutable snapshots updated when subscriptions change. Dispatch is synchronous on the thread that posts the event. Event listener failures now record a bounded diagnostic containing the listener label and event type before the original exception propagates; packet hooks no longer silently discard that context. Priority order is descending, equal-priority insertion is stable, cancellation stops cancellable dispatch, and callback exceptions propagate from the bus. Base registry removal now reports whether an entry was actually removed instead of returning a false-positive mutation result.

Dispatch is not globally single-threaded. Minecraft tick/render hooks normally post from the client/render thread, while the connection channel read hook posts packet-receive events on Netty's I/O thread. Some packet callbacks are deliberately moved to the client thread by vanilla's packet handling. Consumers must therefore treat packet receive events as potentially concurrent with client events. The profiler uses bounded pre-registered statistics and concurrent counters; its disabled dispatch path bypasses timing. AnchorAura and AutoCrystal use deterministic bounded client-thread placement cursors, keeping live world/entity/visibility/damage reads on the owning thread before publication-time revalidation. V8 extends the same ownership rule to Hole, Search and Tunnels: live block-state reads are advanced in bounded client-tick slices, chunk work is deduplicated/cancelled across unloads or runtime generations, and the old fixed-rate Hole worker is removed. [Combat Scan Snapshot Design](COMBAT_SCAN_SNAPSHOT_DESIGN.md) remains the contract for any future off-thread combat implementation.

### Modules, commands and settings

`ModuleRegistry` owns the module instances and explicit registration list. The command registry constructs Brigadier command nodes from the command declarations and keeps aliases in the shared tree. Context profiles, named HUD layouts, integrations, and the profiler are registered through this existing command path; the profiler integration was made additive to the newer command registry.

Settings/configuration are serialized through configurable objects and preset categories. Preset operations use validated names and atomic file writing from the reliability-hardening stack. Failure-atomic JSON application snapshots preset categories and individual startup configurables before application and restores them after uncaught failures while preserving tolerated per-setting/module report-and-continue behavior. V8 also makes preset directory refresh publish only a complete temporary registry, preserves the previous complete registry on iteration failure, restores exact prior bytes on failed replacement, and serves command suggestions from the in-memory registry instead of launching an asynchronous filesystem reload.

### HUD and screens

HUD modules render through the widget renderer and `HudAnchorGroup`. The profiler measures direct widget renderer calls reached through the HUD group; HUD editor previews are intentionally separate from ordinary in-game HUD timing. `HudEditorScreen` owns drag/resize input and delegates reversible layout changes to its history/layout components. Named layouts are stored through the layout store. ClickGUI, HUD Studio, palette, integration and profile screens share client theme/config services, but visual consistency and in-game layout still require human runtime review.

### Persistence and rebuild path

Main configuration objects are serialized as JSON and written through atomic file helpers; presets and named layouts use validated stores. ClickGUI close now captures/deep-copies configurable JSON on the client thread and orders asynchronous save snapshots so stale writes cannot overtake newer state. `ClientDataDirectory` stages legacy directory migration and avoids following links. `ContextProfileRegistry` snapshots preset-category JSON around server changes, restores the baseline before applying another matching profile, and selects rules through the pure `ContextProfileMatcher`. Map-cache input is now a bounded no-follow regular-file format with exact record-size/count validation; unreadable caches are preserved, writes are atomic, asynchronous saves use snapshots, and packet updates are session-owned.

The upstream rebuild script verifies a pinned source commit, preflights ZIP entries, maps paths, creates a staging tree and backs up replaceable destination entries before installation. The workflow keeps a clean Git-root requirement and explicit replacement confirmation; it keeps `.git`, `.github` and `tools` outside the replacement set. V7 modernizes the staging workflow to the maintained Node-24 GitHub Action lines, pushes the successfully rebuilt staging commit before recording artifact provenance, then writes the exact staging commit SHA, runnable-JAR SHA-256 and nested-JAR inventory into the uploaded artifact.

### Networking and integrations

Webhook delivery uses asynchronous Java HTTP requests. Telegram credentials are held in runtime state rather than serialized; the persisted config retains integration type and chat ID, so a Telegram bot token must be re-entered after restart. Notification delivery history is bounded and payload-free. Network operations are not performed while holding the notification queue lock, and delivery tests cover retry/failure paths from the reliability branch. Integration status commands expose configuration and recent delivery state.

### Build and distribution evidence

The ordinary build workflow and the fresh-upstream staging workflow both require one runnable remapped JAR and one source JAR, verify `fabric.mod.json` plus the packaged DiscordIPC Apache-2.0 license/third-party notice, and record artifact provenance. The normal workflow records the tested GitHub commit; the rebuild workflow records the exact successfully pushed staging commit. Both generate `NESTED_JARS.txt` from `META-INF/jars/` so release review can classify what Schizo actually redistributes instead of inferring distribution from Gradle configuration. Direct dependency roles and upstream license evidence are tracked in [Dependency and distribution review](DEPENDENCY_REVIEW.md).

Diagnostic Build #709 traced the Gradle-10 `Task.project` warning to execution-time access of `project.version` in `processResources`. The version is captured during configuration, and Build #722 confirmed the targeted warning is absent. The maintained Node-24 action lines remain in use. V8 Build #845 additionally produced an inspected runnable artifact whose checksum matched its manifest, whose synthetic PR merge tree exactly equaled the tested branch-head tree, whose nested-JAR inventory was empty and whose required runtime metadata/license notices were present.

### Performance instrumentation

`FrameTiming` uses fixed primitive arrays for FPS buckets and bounded rolling frame samples. Rolling average FPS and population frame-time variance use maintained sums; 1% and 0.1% percentile calculations sort reusable scratch storage on a throttled read. The graph has fixed 60 FPS and configurable target/average guides. `EventProfiler` is off by default, times event callbacks only when enabled, and separately records direct HUD widget rendering. Callback/module totals can be inclusive when callbacks post nested events; they must not be summed as frame time. V8 removes several avoidable hot-path costs (palette query/rank rescans, repeated module info/keybind reads, duplicate BreakHighlight bounds work) and reduces VoidESP's candidate enumeration from a 3-D sphere to the exact minimum-Y floor slice. These are source-level reductions, not benchmark claims.

## Multiplayer compatibility audit

The two validation-circumvention modules are removed. This is a source-level compatibility correction, not proof of universal server compatibility. Remaining movement/combat modules can deliberately request client behavior that differs from vanilla expectations; whether a server accepts those packets depends on Minecraft version, server implementation, plugin and module settings. This pass does not claim that such behavior was tested against a controlled server.

The source review disposition and exact unsupported groups are recorded in [Multiplayer Compatibility Review](MULTIPLAYER_COMPATIBILITY.md). The conservative result established here is limited: Schizo no longer ships the two named modules that exist to defeat validation, and the build importer cannot restore them. A full per-module protocol matrix, compatibility activation profile and controlled local-server scenarios remain release work. No public server testing was performed.
